# DASH · Personal Eval Bench
## Platform and desktop design spec · v1.0

**Product:** A local-first desktop workbench for quickly trying any model or agent and deeply inspecting repeatable evaluations across unrelated use cases. The earnings-release pack is a separate reference implementation. Its schema, scoring and decision rules live in a use-case pack, not in the bench itself.

## DASH visual direction

DASH stands for **Domain Assessment & Scoring Harness**. Headline: **Run domain evals. Compare fast.** Keep the approved original icon unchanged: racing-red tile, slanted ivory D and small yellow timing slash. Do not use Ferrari’s horse, shield or wordmark, or imply affiliation.

- Match the supplied Ferrari reference’s contrast: base charcoal `#303030`, deep graphite `#181818`, and racing red `#D82A1C`. Give the outer charcoal background a soft, uneven wash using overlapping diffuse highlight and shadow gradients. Avoid a flat solid or silver base, visible waves, pink and purple. Make the data surface quieter, with slightly lighter gray cards and legible ivory text.
- Keep the sharp diagonal racing composition, but use the racetrack to explain the comparison. Show three original race cars labeled **Open Source**, **Frontier Labs**, and **FineTuned** in the concept artwork, rather than the names of the initial models. These are illustrative candidate types, not fixed or mutually exclusive categories. Actual comparison lanes use the candidates selected by the user. Give each candidate a lane; start every lane at the same dataset version and use a shared checkered finish line for the use case’s business outcomes. The earnings pack shows analyst-ready records, false accepts, and analyst review rate at the finish; other packs supply their own metrics. Display latency, tokens, cost, memory and energy separately as telemetry. Before a measured run, show the same starting position and an explicit empty state, not invented race placements. Leave the track in the result panel, not in the right side of the banner. When a run is processing, show a DASH racing animation. For indeterminate work, animate all three cars together with a soft trail of tire smoke, keep all cars short of the finish line, and never show a winner or ranking; when trustworthy progress exists, map each car’s position to completed cases divided by scheduled cases for that candidate. Do not show a car crossing the finish until that candidate’s run reaches its completed state. Stop motion on completion, cancellation or failure and show the real status. Respect reduced-motion preferences with a static track and text status. The GIF is a design demo with simulated motion, not measured progress or evidence that candidates execute simultaneously. Use pit yellow `#FFD33D` sparingly for the main action and timing accents. Keep status explicit in text, never color alone.
- Show business results first: comparable candidate lanes, run status and a path to the failing case. Below, show compact telemetry. Use an italic wordmark and upright labels.
- Treat the branded shell as a presentation layer. Build the branded desktop shell first; DASH owns results and case drill-down, with optional Opik trace links. Speed in the headline describes quick comparisons, not a guaranteed job runtime.

## Core bench

- **Use-case packs** contain the business decision, requirements and failure costs, input/output schemas, dataset versions and slices, scored examples with separate gold labels, evaluators and acceptance policy. Create cases from requirements, validate their expected outcomes and freeze a holdout. Import or add another pack without touching the runner or results UI.
- **Candidates** are versioned models or agents with a shared invocation/result envelope. Use local Ollama/LM Studio on the M4 and optionally an OpenRouter or other compatible endpoint. An agent version pins instructions, model routing or model list, tools and fixtures; capture step-level traces, retries and errors. Compare agent versions with the same fixtures and permissions. Keep private inputs and judging local by default; hosted execution is opt-in per dataset.
- **Two desktop workflows:** (1) Quick Compare: enter the same query, choose candidates, see responses and traces side by side, and optionally save the query to a development dataset. (2) Dataset Run: choose a pack, dataset version, candidates and scoring policy; queue a repeatable job and compare results to a saved baseline without using a terminal. DASH owns both workflows; Opik is optional for traces and cross-checks. Keep run data exportable independently of Opik.
- **Persistent comparisons:** Store an immutable manifest with dataset/split and case IDs, candidate and prompt/tool revisions, scorer/judge versions, runtime/device and parameters. Keep per-case outputs, scores, failure reasons and trace links. Show paired deltas on identical cases; flag dataset or scoring changes and use overlap or a rerun rather than mixing incompatible scores.
- **Deep results:** Lead with outcome, failure slices and business tradeoffs; drill into a case and its trace in one step. Common measurements include latency, tokens, cost and available local device telemetry. Pack-specific measurements can include correctness, relevance, policy compliance or operational outcomes. Separate measured values from estimates and unavailable metrics. Support rule-based, human and calibrated model-judge scoring; keep their provenance visible.

**Scope for the first build:** Deliver quick compare, a persisted dataset job and case-level drill-down for LFM3, Qwen and Gemma 4 on the finance pack. Prove the generic design with a tiny non-finance fixture (e.g., support-ticket routing with a different output schema and scorer) that runs without core or UI code changes. Design agent versioning into the candidate contract now; implement the first instrumented agent comparison after the three-model pipeline works. Do not build a full agent editor or model training platform upfront.

## Desktop pages

All pages share a keyboard-friendly left rail, a dark title bar, a quiet charcoal work surface and one clear primary action. Use the red diagonal for branded chrome or purposeful calls to action; never wash dense data in saturated red. Keep the surrounding neutral gray softly varied, results surfaces flat enough to scan, and typography and status labels readable at narrow desktop widths. Links, buttons and focus rings must stay distinguishable without color alone.

Use a darker red behind small ivory text where needed for contrast. Implementation target is WCAG AA text and controls, visible focus and meaningful status icons plus labels. Transitions should be brief (about 120–180 ms), off under reduced motion. No flashing or decorative looping outside active processing.

## Electron architecture and device instrumentation

**Decision:** Build a macOS-first Electron app with a web-style UI. Electron is not a prerequisite for reading files or collecting metrics; a browser with a separately installed local daemon can do the same work. Electron is a practical packaging choice for native open/save dialogs, local persistence, managed jobs, and a single app window. It does not grant Full Disk Access or access to protected files, and it does not measure a separate inference process for you.

1. **Renderer:** bundle local UI; sandbox enabled, context isolation on, Node integration off. Typed preload exposes only workspace import/export, job control, approved provider configuration and sanitized metric events. Validate sender and each payload. No arbitrary file paths, shell/exec, IPC forwarding, user HTML injection, or remote content in the privileged app window.
2. **Main process:** owns macOS file pickers, user-selected workspace paths, Keychain-backed credential storage, local SQLite run index, atomic artifact writes and job lifecycle. Normalize and confine file access to approved roots; reject symlink escapes and invalid/oversize inputs. Do not require Full Disk Access. Store immutable run manifests and per-case data under stable `run_id`, `candidate_id`, and `case_id`. Hosted calls and judges require a visible data-egress choice; no silent fallback from local to hosted.
3. **Worker / optional native sidecar:** keep inference/runtime calls and sampling out of the renderer. Begin with Ollama’s native API for token counts and prompt/generation/load durations, plus client time to first visible content and end-to-end time. Add an unprivileged macOS collector for the verified inference process tree if supported: track PID plus start identity and report sampling scope, interval and missing data. Hosted endpoints report only metrics the provider actually returns plus client-side timings. Optional Opik trace export is an integration, not the run database or a required background service.
4. **Scope metrics honestly:** Electron’s `app.getAppMetrics()` describes DASH app processes, not Ollama/LM Studio or whole-machine use; `getGPUInfo()` is device/driver information, not model GPU utilization. Runtime-reported loaded model bytes and process footprint are different, and Apple unified memory is not separate dedicated VRAM. Keep optional system-level GPU or package power in a clearly labeled diagnostic lane, with explicit collection setup and scope; do not equate it with per-model energy. No default sudo, private counters or invented values. Display measured, estimated, not collected and unsupported separately; never substitute zero. Validate idle versus sequential warmed runs on the M4 before publishing any comparison. For calibrated hardware runs, offer a measurement mode with the animation suspended and UI workload held constant; report whether animation was enabled in the run manifest so the renderer’s own GPU and power use are not mistaken for model cost.

References: [Electron native dialogs](https://www.electronjs.org/docs/latest/api/dialog), [Electron security and IPC](https://www.electronjs.org/docs/latest/tutorial/security), [Electron app metrics](https://www.electronjs.org/docs/latest/api/app#appgetappmetrics), [Ollama chat timing fields](https://docs.ollama.com/api/chat), [Apple Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler).

## Platform-to-pack contract

A pack declares `pack_id`, `version`, its description and business decision, input/output schemas, case sets and split rules, evaluator versions, named business metrics (unit, direction, denominator, aggregation), and the acceptance/review policy. Use JSON Schema and data-only manifests before introducing an evaluator plugin API. The platform renders declared metrics and labels dynamically. For example, a support pack may report correct routing and unnecessary escalation; neither workflow gets a platform-wide winner.

A run pins `pack_version`, `dataset_version`, exact case IDs, candidate revisions, prompt and policy hashes, adapters, runtime/backend, and metric collection capabilities. Record effective rather than only requested settings. A case result contains outcome, reasons, evidence references and trace ID; trace and JSON exports use the same immutable identifiers. Keep source and gold access distinct throughout scoring and export. A rerun or re-score gets a new run ID and a link to the original. For paired baseline deltas, show sample size and warn about incompatible datasets or scoring policies.

## Build order and acceptance

1. Shell and local storage with disabled/mock jobs; wire file import, export, keyboard access, and page navigation.
2. Real local runner with one supported case and one intentionally missing-evidence case. Verify the same run/candidate/case IDs in the UI, evaluator output, trace and export. Surface unsupported capability errors instead of swallowing them.
3. Execute the earnings pack on pinned model/runtime configurations; verify results and persist a baseline. Independently load a small support-ticket routing pack with a different schema and scorer, no renderer or runner changes. Treat the checked-in JSONL as dev fixtures, not validation evidence.
4. Add one versioned agent adapter and optional hosted provider, then add validated native telemetry. No general training or agent-builder product in this milestone.

**Pack boundary:** packs own input schemas, data, business outcomes and rules. The platform owns candidate adapters, permissions, jobs, storage, rendering and device telemetry. A pack import is data/configuration, never unrestricted executable code; custom evaluator code must be separately trusted and constrained. See the companion **DASH Use Case 01: Earnings Release Capture** for the first pack. The interactive prototype and GIF use simulated states; no app install or benchmark execution is implied.
